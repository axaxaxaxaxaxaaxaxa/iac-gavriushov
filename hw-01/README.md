## Домашняя работа 1 — вариант 09

Демонстрационный стенд в Yandex Cloud: два веб-сервера в разных зонах за сетевым балансировщиком и один сервер приложения без публичного IP. Настройка Ubuntu 24.04 и nginx выполняется через cloud-init. Внешний порт балансировщика — 80, порт nginx — 8027. Страница содержит `cloudlab on <hostname>`.

## Состав

Префикс по умолчанию: `gavriushov-09-lab`.

| Ресурс | Параметры |
|---|---|
| Сеть | `<префикс>-net` |
| Подсеть A | `<префикс>-subnet-a`, ru-central1-d, 10.19.1.0/24 |
| Подсеть B | `<префикс>-subnet-b`, ru-central1-a, 10.19.2.0/24 |
| Веб-серверы | `<префикс>-web-1`, `<префикс>-web-2`; публичный IPv4, чередование зон A/B |
| Сервер приложения | `<префикс>-app-1`; подсеть A, только внутренний IPv4 |
| Каждая ВМ | standard-v3, 2 vCPU с гарантированной долей 20%, 2 ГБ RAM, HDD 25 ГБ; непрерываемая |
| Балансировщик и целевая группа | `<префикс>-lb`, `<префикс>-tg`; HTTP 80 → порт приложения |
| NAT и таблица маршрутизации | `<префикс>-nat`, `<префикс>-rt`; маршрут 0.0.0.0/0 в подсети A |

## Подготовка

Команды выполняются на локальном компьютере из корня репозитория. Нужны Bash, настроенный Yandex Cloud CLI (`yc`), `jq`, `curl`, `ssh` и `envsubst`. Для профиля `yc` должны быть настроены учётные данные, облако и каталог с правами на создание ресурсов. Должно хватать квот на три ВМ, диски и публичные адреса.

Используются существующие файлы `~/.ssh/id_ed25519` и `~/.ssh/id_ed25519.pub`. Публичный ключ подставляется в cloud-init; приватный остаётся на локальном компьютере. Пользователь внутри ВМ — `student`.

Проверить выбранный каталог без вывода токена:

```bash
yc config get folder-id
yc config get compute-default-zone
```

`cloud-init.yaml` генерируется автоматически из `cloud-init.tpl.yaml` и исключён через `.gitignore`.

## Создание и проверка

```bash
time bash hw-01/create.sh --web-count 2 --env-name lab
# Сразу после команды, до любой другой:
echo "Код возврата: $?"

bash hw-01/check.sh
echo "Код возврата: $?"
```

`create.sh` создаёт ресурсы по порядку зависимостей, затем повторяет проверку готовности с паузой 10 секунд. Цикл ожидания рассчитан на 900 секунд; время уже начавшейся проверки может выйти за эту границу. В ходе настройки cloud-init временные ошибки проверки ожидаемы. Успех — сообщение «Стенд готов» и код 0.

Повторный запуск с теми же параметрами пропускает существующие ресурсы. Он не обновляет параметры уже созданных ВМ, конфигурацию nginx или состав существующей целевой группы. Для изменения конфигурации следует удалить прежнее окружение и создать его заново.

### Параметры create.sh

Приоритет: аргумент командной строки → переменная окружения → значение по умолчанию.

| Аргумент | Переменная | По умолчанию |
|---|---|---|
| `--web-count` | `WEB_COUNT` | `2`, целое число не меньше 2 |
| `--env-name` | `ENV_NAME` | `lab` |
| `--app-port` | `APP_PORT` | `8027`, целое число от 1 до 65535 |
| `--greeting` | `GREETING` | `cloudlab` |

Для имени окружения используйте короткое имя из строчных латинских букв, цифр и дефисов; для приветствия — простое слово без кавычек и управляющих символов. Полной проверки этих строк в скрипте нет.

Пример приоритета: `WEB_COUNT=3 bash hw-01/create.sh --web-count 2 --env-name lab` использует два веб-сервера.

`check.sh` и `destroy.sh` не принимают эти именованные аргументы. Для другого окружения передавайте им переменные. При изменённых порте и приветствии их также нужно передать проверке:

```bash
ENV_NAME=lab APP_PORT=8027 GREETING=cloudlab bash hw-01/check.sh
ENV_NAME=lab bash hw-01/destroy.sh
```

## Что проверяет check.sh

1. Балансировщик возвращает HTTP 200.
2. В 20 запросах встречается больше одного имени веб-сервера.
3. С `web-1` по SSH доступен внутренний HTTP-сервис `app-1` с правильным приветствием.

Код 0 означает успех всех трёх проверок; код 1 — хотя бы одну ошибку. При отсутствии балансировщика скрипт печатает три сообщения о невозможности проверки и возвращает 1.

Если проверка не прошла, сначала посмотрите, какая строка отмечена ошибкой:

- Нет балансировщика: проверьте выбранный каталог, `ENV_NAME` и завершение `create.sh`.
- Нет HTTP 200: проверьте состояние целей, nginx и совпадение порта сервиса с портом проверки балансировщика.
- Отвечает одна машина: проверьте nginx на второй цели. HTTP 200 при этом возможен, но резервирование нарушено.
- Недоступен `app-1`: проверьте SSH к `web-1`, приватный ключ, внутренний IP приложения, nginx и маршрутизацию NAT для установки пакетов. Для диагностики внутри ВМ: `sudo cloud-init status --long`, `sudo systemctl status nginx --no-pager`.

Адреса текущего стенда можно посмотреть через `yc compute instance list` и `yc load-balancer network-load-balancer get --name gavriushov-09-lab-lb`.

## Проверка отказа

```bash
PREFIX=gavriushov-09-lab
WEB_IP=$(yc compute instance get --name "$PREFIX-web-1" --format json \
  | jq -r '.network_interfaces[0].primary_v4_address.one_to_one_nat.address')
TG_ID=$(yc load-balancer target-group get --name "$PREFIX-tg" --format json \
  | jq -r '.id')

ssh -i ~/.ssh/id_ed25519 "student@$WEB_IP" 'sudo systemctl stop nginx'
yc load-balancer network-load-balancer target-states \
  --name "$PREFIX-lb" --target-group-id "$TG_ID"
```

Дождитесь `UNHEALTHY` у первой цели, повторяя последнюю команду. Затем запустите `bash hw-01/check.sh` и сразу `echo "Код возврата: $?"`. Ожидается HTTP 200, ошибка распределения и код 1. Внутренний сервис остаётся доступен: SSH на `web-1` продолжает работать.

```bash
ssh -i ~/.ssh/id_ed25519 "student@$WEB_IP" 'sudo systemctl start nginx'
```

После возвращения обеих целей в `HEALTHY` повторите проверку; ожидается код 0.

## Удаление

```bash
time bash hw-01/destroy.sh
echo "Код возврата: $?"
```

Скрипт ищет ресурсы с началом имени `gavriushov-09-lab-`: сначала удаляет балансировщик и целевую группу, затем ВМ, оставшиеся диски и зарезервированные адреса. После отвязки таблиц маршрутизации удаляет таблицы, NAT, подсети и сеть. Загрузочные диски с `auto-delete=true` удаляются вместе с ВМ; временные публичные адреса освобождаются с владельцами. Личные ресурсы с другими именами не затрагиваются.

Отсутствующие ресурсы пропускаются. Ошибки удаления не подавляются: после устранения причины можно повторить запуск на частично удалённом стенде. Поиск по имени не найдёт вручную переименованный ресурс — не переименовывайте ресурсы стенда до уборки.

Проверка после уборки:

```bash
bash hw-01/check.sh
echo "Код возврата: $?"  # ожидается 1: балансировщик отсутствует

yc compute instance list
yc compute disk list
yc vpc address list
yc load-balancer network-load-balancer list
yc load-balancer target-group list
yc vpc route-table list
yc vpc gateway list
yc vpc subnet list
yc vpc network list
```

Ресурсов стенда в списках быть не должно. Личные ресурсы и сеть `default` могут оставаться. После полного удаления платных ресурсов стенда их дальнейшее потребление прекращается; детализация биллинга может обновиться с задержкой.
